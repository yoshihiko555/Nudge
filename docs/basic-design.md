# 基本設計

## 画面・UX設計

- メニューバーアイコン（テンプレートアイコン推奨）
- 左クリックで小窓の表示/非表示をトグル
- 右クリックでメニュー表示（リフレッシュ/設定/終了）
- 小窓は「進行中タスクのみ」を表示し、Status は表示しない

### 操作導線

1. メニューバーアイコンクリック → 小窓表示
2. タスク横の「完了」「中断」を実行
3. 成功/失敗をトースト表示

## システム構成

- Go (Wails v3) バックエンド
- Wails Webview フロントエンド
- Notion API（REST）

Wails v3 の System Tray 機能とウィンドウ attach 機能を使い、メニューバー常駐と小窓トグルを実現する。

## データフロー

```mermaid
sequenceDiagram
  participant UI as Webview UI
  participant BE as Go Backend
  participant Notion as Notion API

  UI->>BE: RefreshTasks()
  BE->>Notion: Data Source Query（進行中フィルタ）
  Notion-->>BE: Task list
  BE-->>UI: Task DTO list

  UI->>BE: UpdateStatus(taskId, Done|Paused)
  BE->>Notion: Page Update
  Notion-->>BE: Updated page
  BE-->>UI: 更新完了 + 再取得
```

## 非機能要件

- パフォーマンス: 必要なプロパティのみ取得（title/url/last_edited_time 等）
- レート制限: 429 時は Retry-After を尊重しバックオフ
- オフライン: 最終取得結果を表示し「オフライン」表記
- セキュリティ: トークンは Keychain 優先、ログはマスク

## ローカル保存方針

- Keychain: Notion トークン
- 設定ファイル: `~/Library/Application Support/<AppName>/config.json`
  - database_id
  - data_source_id（初回取得後に保存）
  - status_property_name
  - status_in_progress / status_done / status_paused（更新/フィルタ用、UI非表示）
- キャッシュ: `~/Library/Caches/<AppName>/tasks.json`（任意）
- ログ: `~/Library/Logs/<AppName>/app.log`

## 更新戦略

- ポーリング間隔: 60 秒
- 手動リフレッシュあり
- 変更検知: last_edited_time で差分更新
- 更新直後は即時再取得

## ログ設計

- Level: ERROR/WARN/INFO/DEBUG
- トークンや個人情報はマスク

## エラー設計

- 401/403: 権限不足 → 設定画面誘導
- 404: DB/データソース未共有
- 429: バックオフ + Retry-After
- 5xx/timeout: リトライ + UI に警告

### 設計方針

1. **取得と計算を分ける（FR-01・02・05・06・07）**: キャッシュには Notion から取った生データだけを置く。まとまり・並び順・件数・週集計は、RPC の応答とラベル更新のたびに、その時点の今日を基準にした純関数で計算する。0 時をまたいでも、次の表示から振り分けが変わる。
2. **タスクの取得条件（FR-01・03、NFR-01）**: 期日プロパティと完了・中断の値が設定されている DB では、次の条件で 1 回の問い合わせをし、ページ送りで全件取る。`or[ ステータス = 進行中, and[ 期日 ≦ 今日＋8 日, ステータス ≠ 完了, ステータス ≠ 中断 ] ]`。
   - ステータス条件のキーは、既存の `buildStatusFilter` / `buildStatusUpdate`（`client.go:253-275`）と同じく `status_property_type` で `status` か `select` に切り替える。`≠` は同じ切り替えで `does_not_equal` を使う。Status 型は常に値を持つので空のページは起きない。Select 型で空のページが `does_not_equal` に当たるかは実装時に確かめ、当たらない場合は `or[ is_empty, does_not_equal ]` で補う（2 段の上限に収まるよう、そのときは `and` の中を Go 側の判定に寄せる）。
   - フィルタの日付はタイムゾーンを省くと UTC 扱いになるので、1 日の余裕を取り、最終の判定は Go 側でローカル日付に直して行う。期日は期間なら終了日を使う。
   - 条件がそろわない DB は v1 の条件（進行中のみ）で取る。
   - ページ送りは `has_more` が false になるまで `next_cursor` を渡して続ける（ちょうど 100 件のときも `has_more` で終わる）。
3. **習慣の取得（FR-06、NFR-01・05）**: 「今週分」と「過去分」を別の系統で取る。
   - 今週分: 作成日時 ≧ 今週の日曜 0:00（ローカル時刻をオフセット付きで渡す）。毎回のポーリングで、タスクと同じ `refreshAll` の中で取る。今日の一覧と件数は今週分だけから作る（先週のページを代用しない）。
   - 過去分: 52 週前の日曜 0:00 ≦ 作成日時 < 今週の日曜 0:00。`refreshAll` とは別の goroutine と別のロック（`historyMu`）で取り、`refreshMu` を持たない。同時に 1 本だけ走らせ、走っている間の要求は 1 回にまとめる。取り終えたらキャッシュを丸ごと差し替える。取っている間も RPC は前のキャッシュで応える。
   - 過去分を取るきっかけ: 起動時、日付の切り替わり、手動更新（タブの更新ボタンとトレイの「リフレッシュ」。習慣のチェックなど操作の後の再取得では取らない）、設定の保存。キャッシュには「何日の時点で取ったか」を持ち、今日と違えば取り直す。
   - 過去分の失敗: 前のキャッシュを残し、連続達成週数は前のキャッシュで出す。一度も取れていないときは連続達成週数を null（画面では「—」）にする。メニューバーの「!」には含めない。取得結果（API-006）には過去分の失敗として別に載せる。再試行は 5 分 → 15 分 → 60 分と間隔を空け、以後は 60 分ごとにする（毎分は再試行しない）。
4. **メニューバーの件数（FR-05、NFR-04）**:
   - `app.App` は件数が変わりうるとき（ポーリング、手動更新、操作後の再取得、過去分の差し替え、設定の保存）に、ロックを外してから「変わった」という合図だけを、容量 1 の channel に送る（溜まっていれば捨てる）。値は送らない。
   - `main.go` の 1 本の goroutine がその合図を受けるたび、その時点のキャッシュから件数を計算し直して `SetLabel` を呼ぶ。値ではなく合図を送るので、古い件数が後から届いて逆転することはない。`SetLabel` をメインスレッド（RPC やメニューの処理の中）から直接呼ばない。
   - 購読の登録は起動時に 1 回だけ（`SetSummaryNotifier`）。`saveConfig` でポーリングをやり直しても登録は増えない。ポーリングの開始は、登録と `setupTray` の後にする。
   - 表示: DB ごとの最終取得結果（今週分とタスク）のうち 1 つでも失敗があれば「!」。起動して最初の取得が終わるまでと、トークンや有効な DB が無いときはラベルを空にする。
5. **失敗の分類（NFR-06）**: `notion.Client` は HTTP の応答から作る `APIError`（状態コード・Notion のエラーコード）と、通信の失敗（タイムアウト・接続）をそのまま返す。設定の不備（プロパティ名が空など）は `APIError` ではなく、`app` 側の入力チェックの誤り（`ErrInvalidConfig`）として返す。`app` 側でこれらを、権限（401/403）、未共有（404）、レート制限（429）、通信、サーバ（5xx）、設定、の種類に分ける。失敗は DB 名と種類をログに出し、`Poller` に logger を渡して握りつぶさない。トークンはログに出さない。
6. **優先度の順（FR-02・08）**: 設定に「高い順に並べた優先度の値の配列」を保存する。配列に無い値と空は最後に回す。Notion の選択肢の並び順には頼らない。
7. **互換（NFR-02）**: 新しい設定項目は空で既存と同じ動作になる。設定の正規化で既定値を補わない方針（v1）を守る。曜日の列が 7 つそろわない習慣 DB は、週集計をしない。
8. **日付の切り替わり**: ポーリングのたびに前回のローカル日付と比べ、変わっていたら過去分の取り直しを要求し、件数の合図を送る。
9. **設定の保存（FR-08）**: `saveConfig` のあとは、全 DB のキャッシュ（タスク、今週分、過去分）と取得結果を捨てて取り直す。プロパティ名や曜日の列が変わっても、古いデータで計算しない。最初の取得が済んだ印はそのまま残し、取り直しが終わるまでラベルは前の値のままにする。取得の途中で設定が保存されたときに古い結果を書き戻さないよう、設定の世代番号で照合する（詳細設計 5.4・5.5）。
10. **複数 DB**: 小窓のタブは v1 と同じく DB ごとに分かれる（ADR-0007）。まとまりと並び順は DB ごとに API-001 の中で作り、DB をまたいで混ぜない。件数だけは全 DB を合算する（FR-05）。

#### 主な DTO（JSON は snake_case）

- `Task`（既存に追加）: `due_date`（`YYYY-MM-DD`）、`priority`、`group`、`is_in_progress`、`risk`
  - `is_in_progress` は `group` と別に要る。期限切れ・今日のまとまりには進行中と未着手が混ざり、「開始」を出すかどうかはこれで決める
  - `risk` は習慣のときだけ値が入る。v1 から習慣も `Task` で返しているので、それに合わせる（型を分けるのは将来の整理に回す）
- `HabitSummary`（新規、API-003 の応答）: `enabled`、`reason`、`today_index`、`history_loading`、`rows`（`HabitWeekRow` の配列）
- `HabitWeekRow`（新規）: `name`、`url`、`days`（真偽値 7 つ、日〜土）、`checked_count`、`goal`（読めなければ null）、`streak`（null なら「—」）、`streak_capped`（52+ のとき true）、`risk`
- `SyncState`（新規）: `database_key`、`name`、`ok`、`last_attempt_at`、`last_success_at`、`error_kind`、`history_ok`（未試行・対象外は null）、`history_fetched_for`（過去分を取った日付）、`history_error_kind`、`truncated`（件数の上限で打ち切ったか）
- `TraySummary`（内部）: `due_count`、`habit_count`、`has_error`、`ready`

### 非機能要件への対応

| NFR                 | 対応                                                                                                                                                                                           |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| NFR-01 API 呼び出し | 毎分の問い合わせは DB ごとに「件数 ÷ 100 の切り上げ」回だけ。過去の習慣（目安 9 習慣 × 52 週 ≒ 470 件 = 5 回）は起動・日付の切り替わり・手動更新のときだけ。429 は既存の待機つきリトライ（1 リクエストにつき最大 3 回）を使い、リトライもリクエスト数に数える。目安は毎分 2〜4 件、過去分を取り直す 1 分で＋5〜20 件で、60 件以下に収まる |
| NFR-02 互換         | 新しい設定は空で無効。正規化で補わない。v1 の設定ファイルを使った回帰テストを足す                                                                                                              |
| NFR-03 時刻         | `time.Local` を基準にし、時刻と TZ を注入できる純関数にして境界をテストする                                                                                                                    |
| NFR-04 鮮度         | ラベルは DB ごとの取得結果を見て「!」にする。小窓の一覧はキャッシュを出し続ける（ADR-0010 のまま）                                                                                             |
| NFR-05 性能         | 過去分の取り直しは、取得中も前のキャッシュで応答する。HTTP のタイムアウトは既存の 15 秒                                                                                                        |
| NFR-06 診断         | `APIError` → 種類に分類 → ログと API-006 で小窓に出す                                                                                                                                          |
